# Organization-scoped usage compaction (Draft)

> Status: preparatory implementation for [#37484](https://github.com/okou-ai/okou/issues/37484), PR2 of [#37480](https://github.com/okou-ai/okou/issues/37480). **This head scopes discovery and financial work to one organization but retains the existing global coordination protocol. It does not complete global-lock retirement or authorize production activation.** Keep the PR Draft; do not merge, deploy or change the Cron schedule under this request.

## Implemented selection and preserved guarantees

The Cron reads only the **oldest eligible raw row's organization** outside the mutating transaction, using the existing processed status, absent billing error and four-day UTC cutoff. It processes one organization per invocation. There is no fairness cursor, scheduler lock or guarantee that other organizations progress while an older organization's backlog replenishes; the user explicitly removed that requirement.

After obtaining the existing compaction lock, the transaction recomputes the cutoff and selects up to **500 oldest raw seeds in the chosen organization**. The discovery row is only an organization hint: its ID is never a mutation input. Each seed expands to its complete physical grain, including all eligible raw and preexisting hourly facts. The grain includes organization, user, processed hour, Run/billing identity, resource tuple and both allowance-window IDs. Existing `FOR UPDATE` source locking, atomic replacement, reconciliation and signed-`bigint` overflow rollback remain unchanged. A seed limit does **not** bound a grain's physical work; do not introduce temporary same-grain hourly fragments.

An empty eligible discovery snapshot, including held-error-only data, does no financial work and does not acquire the compaction lock. A late or backdated processed row is reconsidered by a later invocation. Error-held rows are not compacted; the existing bounded probe still reports them. Explicitly scoped test requests use owned organization IDs rather than sweeping other tests' rows. The Cron's `hasMore` means **global** eligible raw work, checked within the mutating transaction after its rewrite, not just the chosen organization's remainder. A failure of that receipt read rolls back the rewrite; no required database query is added after commit. On no-work calls `hasMore: false` describes the discovery snapshot, not a fence against later arrivals.

Mutating-batch counters and the bounded held-error probe now describe the **selected organization**. On no-work calls the probe describes the discovery scope (all organizations for Cron, owned IDs for a test request). Only Cron `hasMore` is a global remainder. Do not compare those scoped counters with old cross-org probe values as if their observation scope were unchanged.

Readers and settlement retain quantities, charged credits, allowance-window totals, the original time anchor, synchronous final receipts, FEFO and transactional rollback. No schema, historical migration, Cron configuration, pricing or balance-update change is included.

## Coordination at this head

Nonempty compaction still takes the existing exclusive `usage_event_compaction` transaction key. Ordinary/managed/Social settlement, Agent deletion and threadless Run cleanup retain their original shared participation and lock order. User/organization usage deletion, the explicit attribution backfill and the installed historical `purge_quiescent_provisional_billing_attribution` function retain global exclusive. The separate `credit_<orgId>` protocol is unchanged.

The earlier dual-key scaffold was removed during self-review: retaining global coordination while adding a second organization advisory key provides no additional exclusion, adds round trips to settlement and broadens the historical exemption. [The advisory-lock retirement policy](../advisory-locks.md) applies in review even when lexical lint does not report a new call. Do not expand a stock SQL exemption, add a lock table mechanically or treat a passing lint run as approval for another locking layer.

This head therefore makes **no claim of cross-organization lock independence or a measured net speedup**. Scoping work to one org does not itself allow the global key to retire. Any future replacement must preserve the actual multi-row invariant with the smallest supported transactional boundary and pass the proof and release gates below.

## Remaining proof gates

1. **Normal ownership, not hypothetical corruption.** Normal Run creation scopes an existing Session to the caller's org and writes a new Session and Run with the same org; Sessions do not normally cross organizations. Independent org columns and FKs can represent inconsistent historical/direct-writer rows, but that is not evidence that production contains them. Treat them as a migration obligation only if concrete writer or historical evidence establishes relevance; do not add speculative remediation.
2. **Confirmed multi-org user cleanup.** Raw, hourly and Social deletion is by `user_id`, not one org. A replacement must coordinate the actual affected scope, including concurrent settlement and Run-FK effects. Merely selecting distinct current orgs and later rechecking is not a writer fence; owner IDs on usage/Social are plain text, and pending webhook inserts already bypass the current global key. First distinguish existing races from newly introduced non-equivalent results. Do not remove the existing protocol without a finite proof of amounts, receipts, deletion visibility and lock order.
3. **Old/new writers and rollback.** An old settler holds only global shared. A new compactor holding global shared plus org exclusive would not exclude that same-org old request. Pausing the Cron drains neither API handlers nor operator scripts. The compactor, ordinary/Social settlement, Agent/Run/user/org cleanup, backfill and any callable historical function must share a proven transition or finish draining, including supported rollback targets, before global exclusion can relax. Do not edit migration 1119 in place.
4. **Focused isolated verification.** Exercise duplicate Cron calls, late/backdated rows, cutoff rollover, lost responses, overflow, allowance totals, reader behavior and the necessary cleanup/settlement interleavings through real API routes and uniquely owned data. Follow [API testing](../testing/api-testing.md); do not add lock-waiter observation or internal pause points. Compare round trips, acquisition/wait/hold and whole-batch/reader work under matched synthetic load. Successful-batch telemetry and local timing alone do not establish a production root cause or benefit.
5. **Independent activation gates.** [#36957](https://github.com/okou-ai/okou/issues/36957) owns finite physical-grain work; [#36956](https://github.com/okou-ai/okou/issues/36956) owns compatible settlement. Organization selection does not resolve either [#36958](https://github.com/okou-ai/okou/issues/36958) gate.

## Three-release boundary

PR1 pauses only the usage-compaction Cron; it must **merge and have its production deployment verified** before PR2 may merge. PR2 must be ready enough before the pause to bound backlog and name a safe fallback, and its replacement protocol and old-request drain must be verified after production deployment. Only then may PR3 restore the Cron. A merge, green CI or successful preview is not a production release or proof that in-flight requests ended.

This Draft can be prepared first. No merge, deployment, production SQL/`EXPLAIN`/BUFFERS, backfill execution, or Cron activation/pause is authorized here. A permanent global shared bridge is not a substitute for the global-lock-retirement endpoint.
