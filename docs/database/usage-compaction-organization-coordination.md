# Organization-scoped usage compaction coordination (Draft design)

> Status: implementation-in-progress for [#37484](https://github.com/okou-ai/okou/issues/37484), the middle PR in [#37480](https://github.com/okou-ai/okou/issues/37480). **The Draft branch has a dual-lock compatibility scaffold, not an activated production switch or a proven safe removal of the global key.** Keep the current global lock until the user-deletion and rollout gates below pass. This document is not a production rollout instruction.

## Goal and existing guarantees

Before this Draft, the configured Cron selects up to 500 oldest eligible raw `usage_event` **seeds** across all organizations every minute. This Draft instead discovers the oldest eligible row's organization outside the transaction and selects up to 500 seeds **in that organization** inside the transaction. Each selected physical grain includes `org_id`, `user_id`, processed hour, Run/billing identity, resource tuple, and both allowance-window IDs. It expands to all eligible raw and preexisting hourly facts in that grain, locks them, replaces them with one reconciled hourly fact, and deletes raw in one transaction. The 500-row seed does **not** bound the selected grain's physical work. Readers and settlement must retain quantity, charged credits, per-window allowance totals, the original time anchor, synchronous final receipt, FEFO and complete-grain `bigint` overflow rollback. Do not introduce temporary same-grain hourly fragments to achieve a row cap.

A single exclusive `usage_event_compaction` transaction advisory key currently covers the Cron; settlement, Social inline settlement, Agent deletion and threadless Run deletion take it shared. User/org usage deletion and explicit attribution backfill take it exclusive. The installed historical `purge_quiescent_provisional_billing_attribution` function also names this key. The separate `credit_<orgId>` key protects funding decisions and allowance admission; it is not a drop-in replacement for compaction coordination.

## What the Draft branch currently implements

- The existing helper can name a test-isolated per-org advisory key without adding a new raw SQL callsite. A specifically scoped compaction still takes global **exclusive**, then per-org **exclusive**; the Cron now discovers the oldest eligible org outside the transaction but likewise retains global exclusive while compacting that org. Global shared plus org exclusive would not exclude an old same-org settlement request that only takes global shared. Ordinary settlement, Social, Agent deletion and threadless Run cleanup take global shared then per-org shared. Organization cleanup takes global exclusive then its org exclusive; user cleanup takes global exclusive, inventories the user's distinct raw/hourly/Social/Session/Run org IDs and takes those org keys in sorted order. The operator's explicitly scoped backfill and installed historical function still use only the global key, which remains compatible while scoped compaction holds global exclusive. Both must be drained or explicitly handled before global-key retirement; the repository's no-new-advisory-lock rule does not permit simply adding another raw advisory-lock call in the script. Only after all old settlement instances and in-flight requests have drained may scoped compaction relax global exclusive; removing the global bridge entirely requires the other proof gates.
- A scoped batch with no raw rows, including held-error rows, returns a no-work snapshot after a lock-free probe; a later processed row remains eligible for the next invocation. A held-error-only batch still runs the existing locked path to preserve probe telemetry. This _adds_ an advisory acquisition to each ordinary settlement and is not itself a measured net improvement. The production Cron's oldest-org discovery and per-org full-grain batch are implemented, but the user has explicitly removed any fairness/anti-starvation requirement. Key-only user-deletion proof, mixed-version retirement and cutover are not complete. Do not merge it as the completed performance optimization.

## Candidate org-level protocol (not yet proven)

1. Outside the mutating transaction, read only the oldest eligible raw row's organization with the existing processed/error/four-day cutoff predicate. If none is eligible, return a read-only no-work snapshot; a late row is reconsidered on the next invocation. This deliberately does **not** guarantee other organizations progress while an older organization's rows continually replenish; the user removed that fairness requirement. No cursor table or global scheduler lock is added.
2. Recompute the cutoff and select up to 500 **seeds for that org** after obtaining its transaction-scoped coordination key; never mutate the discovery row ID. Expand every selected grain fully under `FOR UPDATE`, including old hourly facts, and preserve count/total and allowance-window reconciliation. A seed limit is not a physical-grain work cap. Same-org compactions exclude each other; cross-org compaction concurrency requires retiring the temporary global-exclusive bridge. The Cron's `hasMore` continues to mean **global** eligible raw work, checked after the chosen org commits.
3. The ordinary lock order is `compaction:<org>` (shared for settlement/Run maintenance, exclusive for compaction) before `credit_<org>` and before ledger or Run FK rows; Social takes compaction shared before locking its job row and only then takes credit. Per-org `credit_` alone would reverse the Social job/deletion order and extend blocking to allowance admission. A replacement through the existing compaction helper must comply with `api/no-new-advisory-lock`; key collisions can cause false cross-org contention and must not compromise safety.
4. Multi-org user cleanup is a **confirmed scope obligation**: `deleteUserUsageData` deletes raw, hourly and Social jobs by `user_id`, not by one `org_id`. Organization cleanup's Run selection also includes Runs attached to Sessions of its owned Agents, but **normal Run creation scopes an existing Session to the caller's org and writes a new Session and Run with the same org**. A Session does not normally change organizations. The Run->Session FK and ledger->Run FKs do not enforce equality of their independent `org_id` columns, so historically inconsistent or direct-writer data is a _schema-permitted defensive case_, not evidence of normal cross-org Sessions or observed production rows. First establish whether such rows exist or remain writable before treating them as a material migration gate. For user cleanup, a candidate needs the affected org set and ordered acquisitions before ledger locks; test whether row/FK locking and retries provide the existing serializable behavior when a new org appears after discovery. An initial `SELECT DISTINCT org_id` alone is not a writer fence: owner IDs on usage and Social jobs are plain text, and the direct usage webhook inserts pending rows outside this advisory protocol. Do not expand this performance issue into repairing unrelated historical defects.
5. Operator backfill, historical installed functions and old API instances still using the global key must be disabled/drained or covered by a reviewed compatible transition. Pausing the Cron only drains old **compactors**, not concurrent old API settlement or deletion. The selected release sequence is PR1 pause schedule (verify deployed and in-flight calls finished), PR2 switch lock protocol (verify deployed and old API/drain floor), PR3 restore schedule (verify deployed). This Draft PR2 may be prepared before PR1, but cannot merge until PR1's **production release**. No production SQL/EXPLAIN/BUFFERS, backfill or activation is authorized here.

## Concurrent scope expansion that must be proved safe

A user U has retained usage in org A only when deletion scans owner orgs. Deletion locks A. An already-running request can then settle a new U event under an org-B shared key while a B compactor independently holds B's exclusive key. Neither conflicts with A. The user-scoped deletion can miss a newly created B hourly fact depending on SQL statement snapshots; a scan-plus-recheck is not a fence against a commit **after** its last check. The current global exclusive/shared pair serializes settlement and compaction against deletion. **This schedule alone does not prove a new financial defect**: transactions that overlap can sometimes be ordered as deletion-before-settlement, which also allows a later fact under the current key. What remains to prove is that _all_ resulting raw, hourly, Social and receipt states have such an equivalent ordering, including retries and any schema-permitted cross-org Run-FK actions if those are confirmed relevant. The plain-text `user_id` on usage and Social jobs provides no parent FK row that automatically blocks B's new owner association. A writer-side lifecycle fence, complete authority barrier, or compatible global exclusion mechanism may be necessary if row/FK locking and retries cannot supply that equivalence.

## Feasibility gates and alternatives

- **First proof required:** enumerate all live paths that modify eligible/processed usage or Run-FK references; in isolated PostgreSQL force the interleavings for user deletion spanning orgs, direct pending insert followed by settlement, old/new handlers, and a late/backdated eligible row. First verify the Session/Run/usage org-equality invariant in relevant historical and active paths; test cross-org Run-FK actions if those rows are actually possible under the migration contract. Demonstrate no miss, double-count, reversed lock order or deadlock with a stable/fenced owner set. If this cannot be proved, do not remove the global lock.
- **Full-grain gate:** organization scoping does not make one grain finite. [#36957](https://github.com/okou-ai/okou/issues/36957) still owns finite-work proof; [#36956](https://github.com/okou-ai/okou/issues/36956) remains the compatible settlement gate for [#36958](https://github.com/okou-ai/okou/issues/36958).
- **Performance gate:** compare no-work lock acquisitions, same/different-org wait, lock hold, whole-batch physical work, report readers and backlog at matched synthetic load. A faster local statement or successful-batch timing is not evidence of a production net gain. Do not prioritize an index solely for rare `billing_error`-held rows without representative evidence.
- **Alternative if complete removal cannot be proved, after old-instance drain:** use the existing global key **shared** for routine org-scoped compaction and settlement, and a per-org exclusive key; rare cross-org deletion retains global exclusive. This can remove global _exclusive_ contention in normal compaction but still acquires a global shared key, increasing the compactor's lock count. It is an explicit product/performance trade-off and **does not meet** the stated global-lock-retirement endpoint. Do not silently substitute it as the final result.

Stop the Draft at this checkpoint unless the cross-org closure and rollout proof can be provided. Its presence or green documentation checks must never be treated as permission to merge PR2 or to pause/resume the production Cron.
