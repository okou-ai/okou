# Organization-scoped usage compaction coordination (Draft design)

> Status: investigation for [#37484](https://github.com/okou-ai/okou/issues/37484), the middle PR in [#37480](https://github.com/okou-ai/okou/issues/37480). **No organization-scoped protocol has been activated or proven safe for merger.** Keep the current global lock until the cross-org deletion and rollout gates below pass. This document is not a production rollout instruction.

## Goal and existing guarantees

The current production Cron selects up to 500 oldest eligible raw `usage_event` **seeds** every minute. Each selected physical grain includes `org_id`, `user_id`, processed hour, Run/billing identity, resource tuple, and both allowance-window IDs. It expands to all eligible raw and preexisting hourly facts in that grain, locks them, replaces them with one reconciled hourly fact, and deletes raw in one transaction. The 500-row seed does **not** bound the selected grain's physical work. Readers and settlement must retain quantity, charged credits, per-window allowance totals, the original time anchor, synchronous final receipt, FEFO and complete-grain `bigint` overflow rollback. Do not introduce temporary same-grain hourly fragments to achieve a row cap.

A single exclusive `usage_event_compaction` transaction advisory key currently covers the Cron; settlement, Social inline settlement, Agent deletion and threadless Run deletion take it shared. User/org usage deletion and explicit attribution backfill take it exclusive. The installed historical `purge_quiescent_provisional_billing_attribution` function also names this key. The separate `credit_<orgId>` key protects funding decisions and allowance admission; it is not a drop-in replacement for compaction coordination.

## Candidate org-level protocol (not yet proven)

1. Outside the exclusive mutating transaction, read the oldest eligible raw events with the current status, error and four-day UTC-cutoff predicate. An adjustable initial discovery window around 500 is a candidate **organization selector**, not a work limit. Deduplicate org IDs, handle an empty snapshot without taking an exclusive lock only if late-arrival and `hasMore` snapshot semantics are explicit, and choose a small number of orgs per invocation. Merely retrying the first 500 can starve other orgs behind one continuously heavy or failing org; a fair bounded rotation/skip mechanism must be justified and tested.
2. For each chosen org, recompute the cutoff and select candidate grains **after** obtaining that org's transaction-scoped coordination key; never mutate the read-only discovery IDs. Use the existing full-grain `FOR UPDATE` source selection, old hourly replacement, count/total and allowance-window reconciliation. Same-org compactions exclude each other; different orgs may work concurrently. `hasMore` must retain an explicit global or org-scoped meaning rather than silently changing the existing Cron response.
3. The ordinary lock order is `compaction:<org>` (shared for settlement/Run maintenance, exclusive for compaction) before `credit_<org>` and before ledger or Run FK rows; Social takes compaction shared before locking its job row and only then takes credit. Per-org `credit_` alone would reverse the Social job/deletion order and extend blocking to allowance admission. A replacement through the existing compaction helper must comply with `api/no-new-advisory-lock`; key collisions can cause false cross-org contention and must not compromise safety.
4. Multi-org cleanup is the **unresolved correctness obligation**. `deleteUserUsageData` deletes raw, hourly and Social jobs by user across organizations. Organization deletion includes Runs reached via its owned Sessions even when those Runs belong to another org; deleting a Run can set `run_id` null on that foreign org's raw/hourly facts. A candidate needs the complete affected org set, sorted exclusive acquisitions **before** ledger/parent locks, and a fence or full transaction rollback/retry if a new affected org appears after discovery. Candidate sets include direct owner rows, all relevant raw/hourly/Social owner orgs, target Runs and the orgs of raw/hourly rows referring to those Runs. An initial `SELECT DISTINCT org_id` is insufficient: usage and Social owner IDs are plain text, not principal FKs, and the direct usage webhook inserts pending rows outside this advisory protocol. Compare each race against current global-lock behavior; do not expand this performance issue into repairing unrelated historical defects.
5. Operator backfill, historical installed functions and old API instances still using the global key must be disabled/drained or covered by a reviewed compatible transition. Pausing the Cron only drains old **compactors**, not concurrent old API settlement or deletion. The selected release sequence is PR1 pause schedule (verify deployed and in-flight calls finished), PR2 switch lock protocol (verify deployed and old API/drain floor), PR3 restore schedule (verify deployed). This Draft PR2 may be prepared before PR1, but cannot merge until PR1's **production release**. No production SQL/EXPLAIN/BUFFERS, backfill or activation is authorized here.

## Feasibility gates and alternatives

- **First proof required:** enumerate all live paths that modify eligible/processed usage or Run-FK references; in isolated PostgreSQL force the interleavings for user deletion spanning orgs, foreign-org Session/Run deletion, direct pending insert followed by settlement, old/new handlers, and a late/backdated eligible row. Demonstrate no miss, double-count, reversed lock order or deadlock with a stable/fenced owner set. If this cannot be proved, do not remove the global lock.
- **Full-grain gate:** organization scoping does not make one grain finite. [#36957](https://github.com/okou-ai/okou/issues/36957) still owns finite-work proof; [#36956](https://github.com/okou-ai/okou/issues/36956) remains the compatible settlement gate for [#36958](https://github.com/okou-ai/okou/issues/36958).
- **Performance gate:** compare no-work lock acquisitions, same/different-org wait, lock hold, whole-batch physical work, report readers and backlog at matched synthetic load. A faster local statement or successful-batch timing is not evidence of a production net gain. Do not prioritize an index solely for rare `billing_error`-held rows without representative evidence.
- **Alternative if complete removal cannot be proved:** use the existing global key **shared** for routine org-scoped compaction and settlement, and a per-org exclusive key; rare cross-org deletion retains global exclusive. This can remove global _exclusive_ contention in normal compaction but still acquires a global shared key, increasing the compactor's lock count. It is an explicit product/performance trade-off and **does not meet** the stated global-lock-retirement endpoint. Do not silently substitute it as the final result.

Stop the Draft at this checkpoint unless the cross-org closure and rollout proof can be provided. Its presence or green documentation checks must never be treated as permission to merge PR2 or to pause/resume the production Cron.
