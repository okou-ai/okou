# Billing hot-path baseline for #36891 / PR1

This is a **measurement protocol**, not a production census or approval to run one. Do not infer hard limits from a masked recent sample. **Owner access boundary (2026-09-27): production data reads are allowed only through bounded MaskDB structured read-only queries; do not connect directly to the production database or run production SQL, `EXPLAIN`, or BUFFERS.** Use isolated local PostgreSQL for plans and behavior/overhead tests; its plan is not a production plan. Name the environment and comparable load interval, redact organization/member IDs and query literals from shared results, and record each sample's wall-clock interval, scope, page bounds, complete/truncated flag and snapshot limitations. Do not alter usage, money, indexes, timeouts or worker schedules as part of a baseline.

## Runtime observations

Billing timings use the existing Axiom operation-timing SDK transport into `vm0-sandbox-op-log-${AXIOM_DATASET_SUFFIX}`. Filter `source = "api"` and `operation_domain = "billing"`; each event has a fixed `op_type`, numeric `duration_ms`, and `success = true` for a completed invocation, **not** a claim that an admission or individual charge succeeded. Billing events deliberately omit `run_id` and `sandbox_type`: a settlement/cron batch does not necessarily belong to one run or sandbox. No org, user, run, event or pricing identifiers appear in dimensions. Query these events separately from the `vm0-web-logs-*` application logs and from run-associated admission timers; the datasets are not interchangeable.

| `op_type`                                                                             | Boundary and dimensions                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `api_billing_settlement_work`                                                         | Inside settlement, including its lock waits but **excluding COMMIT and earlier inline managed locks**. `timing_scope` is `standalone` or `inline`; `pending_events`, `pricing_rows`, `affected_users`, `grant_rows`, `expired_rows`, `expiry_rows` count already-selected work, not physical reads or only modified rows. Paired wall-clock phase dimensions are defined below. Emitted after the caller's money transaction commits, for nonempty batches only. |
| `api_billing_settlement_compaction_lock_wait`, `api_billing_settlement_org_lock_wait` | Lock-acquisition durations measured within the settlement call. Inline callers may have acquired the locks earlier; these measurements exclude that earlier wait. `timing_scope` distinguishes inline from standalone.                                                                                                                                                                                                                                           |
| `api_billing_settlement_transaction`                                                  | Standalone settlement only: entire `db.transaction` including COMMIT, excluding postcommit delivery; **absent for inline managed/Social transactions**.                                                                                                                                                                                                                                                                                                          |
| `api_billing_allowance_availability`, `api_billing_allowance_org_lock_wait`           | Advisory availability transaction duration including COMMIT, and its org lock wait. `available` on the first row means a plan availability was returned, **not** that a later run/job was admitted. In-transaction callers are not included.                                                                                                                                                                                                                     |
| `api_billing_usage_compaction_batch`, `api_billing_usage_compaction_lock_wait`        | Successful compaction batch including COMMIT, and compaction lock wait. The batch row has `raw_seed_limit`, `seeded_raw_rows`, `selected_grains`, `raw_rows_deleted`, `hourly_rows_deleted`, `hourly_rows_inserted`, `billing_error_held_rows`, `logical_input_rows`, `logical_compression_ratio`, `has_more`. **`raw_seed_limit = 500` is not a whole-grain cap.**                                                                                              |

Inline Social settlement reuses compaction and credit protection already held by
its caller. Its settlement lock-wait observations are therefore zero after the
redundant acquisitions are removed. They still exclude the earlier waits; zero
is not evidence that the larger Social transaction encountered no contention.

Settlement phases use monotonic `performance.now()` around awaited blocks, rounded to 0.001 ms: `pending_read_ms` and `pricing_read_ms` include SELECT round-trip and decoding; `pricing_calculation_ms` covers local pricing work; `allowance_ms` includes locked allowance work; `event_write_ms` includes the bulk processed-event update; `grant_deduction_ms` includes per-user grant reads/writes; `org_credit_ms` includes reads, expiry, debit and balance-alert decision when shared credits are charged. `org_credit_ms = 0` means the conditional stage was skipped for a **committed nonempty** settlement. All other stage fields are present for such a settlement even when their work is short; fields absent on earlier rows or no event for an empty/failed/rolled-back attempt are **unknown**, not zero. They are application wall time, not isolated SQL execution or physical reads. Local work and locks outside the named intervals, rounding, and inline callers' outer transaction mean the stage sum need not equal `duration_ms`; do not subtract separately aggregated percentiles to apportion a transaction.

Emit after commit via asynchronous, best-effort ingestion; ordinary synchronous telemetry failures cannot turn a committed receipt into a failed response (cancellation still propagates). A rolled-back transaction or batch error has no completed timing events. Lost postcommit acknowledgements can replay completion and timing events. There is no attempt identifier on these privacy-safe rows, so do not join unrelated op types by timestamp or add their independently aggregated percentiles. At comparable load, separately compute p50/p95/p99 and maximum per `op_type`, plus per-batch counts and worker backlog. Use distinct time windows and note the tail's observation count; zero successful observations is **unknown**, not proof of no pending usage. Compare to before-code baseline and check both successful and failed path logs. A runtime duration is not a database buffer/execution count.

## Bounded read-only diagnostics

Use the MaskDB structured API for production data: name a finite time interval, exact table/columns/filters, fixed page size and page cap **before** querying. Keep masked identifiers private; publish only aggregates that cannot identify an organization, user or run. Report returned/allowed rows, pages, completeness, truncation and the fact that separate pages/tables may not share a snapshot. A bounded sample or the gateway's index metadata cannot establish whole-population tails, actual index use, production physical buffers or an absolute work cap. If complete coverage is required for a safe rewrite but unavailable through MaskDB, pause that rewrite rather than silently extrapolate.

Only on an **isolated local PostgreSQL instance** may we run SQL plans and matched before/after tests for the generated pending, pricing, grant, expiry and report queries. A local `EXPLAIN (ANALYZE, BUFFERS)` measures local work and may execute its statement; use synthetic/fixture data and do not point its connection string at production. Record local database version, test schema, row shapes and limits; neither a local plan nor its BUFFERS establishes production physical reads. A final `LIMIT` does not bound rows scanned below a GROUP BY or JOIN.

**Period-boundary observation on current main:** `usage-record.service.ts` calls `normalizeFinalizedUsagePeriod`, which rounds both report bounds **up to the next whole hour** before filtering raw `processed_at` and hourly `processed_hour`. A raw usage event first committed after a non-hour-aligned billing-period start but before that next hour can be outside the displayed `billingPeriod`, despite its `processed_at` being within the nominal subscription period. This is observed behavior, not a proposed correction or evidence that first settlement should be backdated; the whole-hour cross-period regression fixture deliberately avoids this separate first-hour gap. PR8 must resolve whether correcting it changes a business-visible report and obtain approval before assuming that timestamp membership alone is the old API contract.

For a compaction grain tail, inspect the **exact** nullable-key grouping used by `candidateCtes` and `lockedSourceCtes` in `cron-compact-usage-events.service.ts`: processed hour, org, user, run, billing run/anchor/context, kind, provider, category, short and weekly window IDs. The selected seed may expand to every raw event and matching hourly row in that grain; `seededRawRows` alone is not a fanout measure. Use a scoped read-only grouped histogram including late arrivals and four-day retention; a top-N without a complete inventory cannot bound the maximum. For report reads include raw and hourly query plans for page and `range=all` totals at matched period/scope, and verify `processed_at` versus `processed_hour` boundaries.

## Decision gate for PR4 / PR6 / PR8

Publish actual sample size/completeness, observed tail and numerical p95/p99/lock/read budgets **only where the permitted measurements support them**. If MaskDB cannot prove a required physical bound (including one event's grant/expiry fanout or one compaction grain), leave the associated rewrite paused rather than asserting a whole-population cap. The current settlement pending SELECT has no `ORDER BY`; any new page or priority can change allowance and FEFO outcomes. If finite work, source order and exact final receipt cannot coexist with the old behavior, pause the affected slice and request a product decision. No measurement, production sweep or money correction is authorized by this runbook.
