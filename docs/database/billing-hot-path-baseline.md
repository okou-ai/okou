This is a **measurement protocol**, not a production census or approval to run one. Do not infer hard limits from a masked recent sample. **Owner access boundary (2026-09-27): production data reads are allowed only through bounded MaskDB structured read-only queries; do not connect directly to the production database or run production SQL, `EXPLAIN`, or BUFFERS.** Use isolated local PostgreSQL for plans and behavior/overhead tests; its plan is not a production plan. ## Runtime observations

Billing timings use the existing Axiom operation-timing SDK transport into `vm0-sandbox-op-log-${AXIOM_DATASET_SUFFIX}`. Filter `source = "api"` and `operation_domain = "billing"`; each event has a fixed `op_type`, numeric `duration_ms`, and `success = true` for a completed invocation, **not** a claim that an admission or individual charge succeeded. Billing events deliberately omit `run_id` and `sandbox_type`: a settlement/cron batch does not necessarily belong to one run or sandbox. No org, user, run, event or pricing identifiers appear in dimensions. Query these events separately from the `vm0-web-logs-*` application logs and from run-associated admission timers; the datasets are not interchangeable.

| `op_type`                                                                             | Boundary and dimensions                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `api_billing_settlement_work`                                                         | Inside settlement, including its lock waits but **excluding COMMIT and earlier inline managed locks**. `timing_scope` is `standalone` or `inline`; `pending_events`, `pricing_rows`, `affected_users`, `grant_rows`, `expired_rows`, `expiry_rows` count already-selected work, not physical reads or only modified rows. Paired wall-clock phase dimensions are defined below. Emitted after the caller's money transaction commits, for nonempty batches only.                                                                                                                                                    |
| `api_billing_settlement_compaction_lock_wait`, `api_billing_settlement_org_lock_wait` | Lock-acquisition durations measured within the settlement call. Inline callers may have acquired the locks earlier; these measurements exclude that earlier wait. `timing_scope` distinguishes inline from standalone.                                                                                                                                                                                                                                                                                                                                                                                              |
| `api_billing_settlement_transaction`                                                  | Standalone settlement only: entire `db.transaction` including COMMIT, excluding postcommit delivery; **absent for inline managed/Social transactions**.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `api_billing_allowance_availability`, `api_billing_allowance_org_lock_wait`           | Advisory availability transaction duration including COMMIT, and its org lock wait. `available` on the first row means a plan availability was returned, **not** that a later run/job was admitted. In-transaction callers are not included.                                                                                                                                                                                                                                                                                                                                                                        |
| `api_billing_usage_compaction_batch`, `api_billing_usage_compaction_lock_wait`        | Successful compaction batch including COMMIT, and compaction lock wait. The batch row has `raw_seed_limit`, `seeded_raw_rows`, `selected_grains`, `raw_rows_deleted`, `hourly_rows_deleted`, `hourly_rows_inserted`, `billing_error_held_rows`, `logical_input_rows`, `max_grain_source_rows`, `logical_compression_ratio`, `has_more`. `max_grain_source_rows` is the largest number of raw plus preexisting hourly source rows in one full physical grain **processed in that successful batch** (zero for an empty batch); it contains no grain identifier. **`raw_seed_limit = 500` is not a whole-grain cap.** |

Inline Social settlement reuses compaction and credit protection already held by
its caller. Its settlement lock-wait observations are therefore zero after the
redundant acquisitions are removed. They still exclude the earlier waits; zero
is not evidence that the larger Social transaction encountered no contention.

Settlement phases use monotonic `performance.now()` around awaited blocks, rounded to 0.001 ms: `pending_read_ms` and `pricing_read_ms` include SELECT round-trip and decoding; `pricing_calculation_ms` covers local pricing work; `allowance_ms` includes locked allowance work; `event_write_ms` includes the bulk processed-event update; `grant_deduction_ms` includes per-user grant reads/writes; `org_credit_ms` includes reads, expiry, debit and balance-alert decision when shared credits are charged. `org_credit_ms = 0` means the conditional stage was skipped for a **committed nonempty** settlement. All other stage fields are present for such a settlement even when their work is short; fields absent on earlier rows or no event for an empty/failed/rolled-back attempt are **unknown**, not zero. They are application wall time, not isolated SQL execution or physical reads.

The same work row additionally breaks down two existing outer phases, without extra SQL, operation rows or ingestion calls. Within `allowance_ms`, `allowance_allocation_read_ms` covers the existing-allocation lookup; `allowance_anchor_ms` covers unresolved-candidate selection and run-anchor resolution; `allowance_window_lock_ms` covers the issued short/weekly window read and its row-lock wait (or the no-candidate early return); `allowance_window_issue_ms` covers conditional entitlement lookup and missing-window inserts; `allowance_allocate_ms` covers in-memory allocation; `allowance_window_write_ms` covers changed-window consumption persistence; and `allowance_allocation_write_ms` covers new allocation-row persistence. These blocks execute in that order; some may do only local work or no SQL. Within `org_credit_ms`, `org_balance_read_ms` covers the pre-expiry balance read, `org_expire_credits_ms` covers expired-lot locking/expiration and any corresponding balance update, `org_debit_ms` covers the debit UPSERT (including its existing entitlement-wrapper work), and `org_expiry_lot_deduction_ms` covers live expiry-lot locking/deduction. The low-balance decision and timer overhead remain in the enclosing phase but not a named child. All eleven numeric child fields are present on new successful nonempty work rows; when member grants fund all usage, the four conditional org-credit child fields and `org_credit_ms` are **zero because that block was skipped**. A rounded zero for another child does not prove that no code ran or no database statement was issued. Missing child fields on an older event, and missing work events for empty, rolled-back or failed attempts, are unknown, not zero.

Subtract the sum of each phase's children from **that same row's** enclosing `allowance_ms` or `org_credit_ms` for its unnamed local-work/timer/rounding residual; small negative values may result from 0.001-ms rounding and must not be clamped. Inner durations are application wall time including awaits and decoding, not exclusive SQL time or physical reads. When selecting a fixed postdeployment UTC analysis window, report successful work counts and all-child-field coverage first, split standalone from inline, and only attribute complete **same-event** rows (including a stated slow cohort). Retain the earlier no-child population separately. Do not claim production-wide p99, physical query cost or a speedup from this instrumentation.

The work event also carries `compaction_lock_wait_ms` and `org_lock_wait_ms`: the same already-measured, whole-millisecond-rounded durations published in the two separate lock-wait operation rows. Both locks are acquired within the measured work boundary for standalone settlement. For inline managed/Social callers that already hold them, these fields measure only lock acquisition **inside the settlement call** (which can be zero), not earlier waits in the outer transaction. On a **single work row with every field present**, `duration_ms - compaction_lock_wait_ms - org_lock_wait_ms -` the sum of the seven phase fields is the unnamed local-work/timing residual. Whole-millisecond rounding of total and locks versus 0.001-ms phases can make a small residual negative; do not clamp it or interpret it as physical database time. Missing lock fields on older work rows are **unknown**, not zero. Do not join separate operation rows by timestamp or subtract their independently aggregated percentiles to apportion a transaction.

After a version with the paired lock fields is deployed, select a fixed UTC window containing only complete-field successful work rows, report the window and total/missing-field counts, and split standalone from inline before calculating same-row work, stage, lock, and residual distributions (including the slow cohort). This is postdeployment evidence, not a pre-merge gate or a claim of a production-wide p99, complete attempt coverage, physical reads, or a latency improvement.

Emit after commit via asynchronous, best-effort ingestion; ordinary synchronous telemetry failures cannot turn a committed receipt into a failed response (cancellation still propagates). A rolled-back transaction or batch error has no completed timing events. Lost postcommit acknowledgements can replay completion and timing events. There is no attempt identifier on these privacy-safe rows, so do not join unrelated op types by timestamp or add their independently aggregated percentiles. At comparable load, separately compute p50/p95/p99 and maximum per `op_type`, plus per-batch counts and worker backlog. Use distinct time windows and note the tail's observation count; zero successful observations is **unknown**, not proof of no pending usage. Compare to before-code baseline and check both successful and failed path logs. A runtime duration is not a database buffer/execution count.

## Bounded read-only diagnostics

Use the MaskDB structured API for production data: name a finite time interval, exact table/columns/filters, fixed page size and page cap **before** querying. Keep masked identifiers private; publish only aggregates that cannot identify an organization, user or run. Report returned/allowed rows, pages, completeness, truncation and the fact that separate pages/tables may not share a snapshot. A bounded sample or the gateway's index metadata cannot establish whole-population tails, actual index use, production physical buffers or an absolute work cap. If complete coverage is required for a safe rewrite but unavailable through MaskDB, pause that rewrite rather than silently extrapolate.

Only on an **isolated local PostgreSQL instance** may we run SQL plans and matched before/after tests for the generated pending, pricing, grant, expiry and report queries. A local `EXPLAIN (ANALYZE, BUFFERS)` measures local work and may execute its statement; use synthetic/fixture data and do not point its connection string at production. Record local database version, test schema, row shapes and limits; neither a local plan nor its BUFFERS establishes production physical reads. A final `LIMIT` does not bound rows scanned below a GROUP BY or JOIN.

**Period-boundary observation on current main:** `usage-record.service.ts` calls `normalizeFinalizedUsagePeriod`, which rounds both report bounds **up to the next whole hour** before filtering raw `processed_at` and hourly `processed_hour`. A raw usage event first committed after a non-hour-aligned billing-period start but before that next hour can be outside the displayed `billingPeriod`, despite its `processed_at` being within the nominal subscription period. This is observed behavior, not a proposed correction or evidence that first settlement should be backdated; the whole-hour cross-period regression fixture deliberately avoids this separate first-hour gap. PR8 must resolve whether correcting it changes a business-visible report and obtain approval before assuming that timestamp membership alone is the old API contract.

For a compaction grain tail, inspect the **exact** nullable-key grouping used by `candidateCtes` and `lockedSourceCtes` in `cron-compact-usage-events.service.ts`: processed hour, org, user, run, billing run/anchor/context, kind, provider, category, short and weekly window IDs. The selected seed may expand to every raw event and matching hourly row in that grain; `seededRawRows` alone is not a fanout measure. The emitted `max_grain_source_rows` samples selected, successfully committed batches only: it excludes unselected grains, failed or rolled-back attempts and index work, and it is neither a physical BUFFERS measure nor a population or future hard maximum. Older event rows without this field are unknown, not zero. Use a scoped read-only grouped histogram including late arrivals and four-day retention if a complete population bound is required; a top-N without a complete inventory cannot bound the maximum. For report reads include raw and hourly query plans for page and `range=all` totals at matched period/scope, and verify `processed_at` versus `processed_hour` boundaries.

Publish actual sample size/completeness, observed tail and numerical p95/p99/lock/read budgets **only where the permitted measurements support them**. If MaskDB cannot prove a required physical bound (including one event's grant/expiry fanout or one compaction grain), leave the associated rewrite paused rather than asserting a whole-population cap. If finite work, source order and exact final receipt cannot coexist with the old behavior, pause the affected slice and request a product decision.
