# Runner WSS listener and admission (#37027)

This is a **draft, non-activating** Runner slice under #36981. Do not merge/deploy it before the prerequisites below. It does not make the direct browser-to-Guest channel work by itself. In particular, the production Guest attachment is deliberately unavailable until #37026 supplies its private run-scoped channel; the listener rejects a first frame without consuming a ticket or sending `auth.ok`. The protocol tests use an inert echo adapter, not a production Guest implementation.

## Health and host contract

Official Runners (not `runner local` test/development jobs) require a pre-existing trusted `/run/okou-ws` directory. The Runner holds its exclusive base-dir/identity lock, validates the directory and binds `<runner_id>.sock` without unlinking an existing path, then starts its supervised accept task before provider readiness, healthy status, heartbeat or claiming. Missing/unsafe/symlinked directories, permissions or an existing socket fail startup. An accept task failure stops healthy claims/heartbeats and follows normal Runner teardown. Sockets are removed only if their file identity remains the one created by the process. Soft-draining Runners retain their own listener while they still have runs; release-specific Runner IDs do not share a socket. This is not a separate host lease or health prober.

#37028 must provision the directory and group-access policy **before** this mandatory-listener Runner is deployed. The staged host contract is `/run/okou-ws` owned `root:okou-wss-caddy` at mode `0710` (not setgid). The Runner verifies that owner/group and the exact directory mode `0710`, applies the parent group to its bound socket by file descriptor and sets mode `0660`; the host must restrict group membership. Neither the Runner nor this PR creates DNS/TLS, Caddy routing or public firewall exposure. There is no API issuance switch: #37025 already permits explicit, owner-authenticated on-demand bootstrap with a 30-second one-use ticket. A candidate target is not proof of ingress readiness. No production Web adapter or ingress activation is authorized here.

## Wire and ownership

Caddy should forward only `/ws/<runner_id>` to the matching socket. The listener refuses other paths, query strings, ordinary HTTP and malformed WebSocket handshakes. It allows at most 32 connected tasks and 16 simultaneous pre-auth handshakes, with a five-second total pre-auth deadline. The first application frame is JSON `{"runId":"<uuid>","ticket":"<43-character-base64url>"}` (maximum 256 bytes). The token is never part of the URL or logs. Using its configured and validated hostname, the Runner requests #37025's official-Runner ticket consumption with the exact run, runner ID and `wss://<hostname>:443` origin; a non-success, outage or mismatched response is denied.

The destination process then checks its **current** `ActiveRuns` guard and in-memory `StatusTracker` Running-phase `(runId,sandboxId)`, not a status file, DB row, hostname/path, heartbeat generation or parked-sandbox cache. It rechecks after consume and after the Guest attachment operation. #37026's planned `RunGuestChannels::open(run_id)` must atomically resolve and hold the live executor assignment epoch; the status mapping alone does not grant Guest access. Only then does it send `{"type":"auth.ok"}`. Subsequent Guest messages are opaque binary frames up to 64 KiB. The channel adapter must cap each direction to 16 pending frames (1 MiB), preserve ordering and close on run-end/hard stop. Connection work is backpressured and canceled on the process-local run guard's release; a 250 ms live status check covers early in-memory removal. Stalled writes have a finite deadline. Any non-binary application message after authentication closes the stream.

## Unresolved integration / rollout gates

1. #37026 must supply the real private Guest attachment and atomically validate the same live `runId` assignment, including its sandbox epoch; until then the production listener remains fail-closed. Keep this PR draft and unmerged while that seam is unresolved.
2. #37025's `revoke` endpoint currently invalidates **only unconsumed** ticket digests. It provides no notification to a Runner for already-established streams. Runner closes streams on run completion and hard stop, but **cannot yet guarantee immediate stream closure on an independent owner revoke**. That requires an explicit control-plane revocation signal/epoch and a test before claiming #37027's revocation acceptance criterion; do not infer it from ticket consumption or poll unboundedly. This is an outstanding integration blocker, not a silent success.
3. Provision/verify #37028's host directory, Caddy/TLS and peer permissions before shipping the mandatory listener. Complete #37029 and #37030's non-production browser-to-Guest E2E, drain pre-WSS serving Runners and Runs, verify every selectable hostname, and obtain separate production activation authorization. #37074 retention cleanup is separate and postponed. Rollback after a Web caller is enabled needs separately reviewed client-side containment because no issuance flag exists.
