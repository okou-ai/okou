## Exact public replacements and changed assertions

- **Usage Pack credits:** authenticated `POST /api/billing/usage-pack-checkout` writes the purchase intent and sends metadata to Stripe. The mock captures that actual outbound metadata, including the server-created subscription identity, and returns it through `POST /api/webhooks/stripe` (`invoice.paid`). Stripe owns invoice amounts, recurring periods, Product bonus metadata and subscription state; the mock does not write application rows. User/member/admin `GET /api/billing/usage-pack-credits` observes the results. Normal `$20` / `$50` packs yield `20,000 + 400` / `50,000 + 2,600` credits. An ordinary check-in gives100 credits with168-hour expiry; advancing the existing test clock from August2 to10 proves expired check-in exclusion. Purchased/bonus invoice periods end September9. Former arbitrary10,000 and4,350 bonuses and independently chosen expirations are lost, not reproduced through a hidden writer. Stripe signature verification is mocked at the SDK boundary, so this is not a cryptographic signature test.
- **Invitations:** normal Clerk-authenticated onboarding completion replaces direct organization/entitlement inserts. Clerk invitations and signed membership callbacks still drive all seven declarations/nine executions, including the15-slot cap, cross-org dedupe, replay and acceptance racing the external send response. Only provider responses are mocked.
- **Billing token:** provider invoices create purchased/Pro credits; normal onboarding, personal provider OAuth, Agent/chat creation and actual Runner heartbeat/claim yield the token read from its encrypted environment. Billing GET returns120,000 credits (100,000 purchase plus20,000 Pro grant). Normal cancellation ends the Run. - **Weather:** `prepareFreeWeatherActor` now uses the existing normal onboarding/Stripe Pro fixture and ordinary Weather/AirQuality HTTP responses. Other consumers of that shared fixture are not certified by this change.
- **Share rewards:** ordinary status/check-in and submission routes retain canonical URLs, pending state, same-owner idempotency, concurrent same-post submission and distinct cross-org claims. Since the public quest is user-scoped, both org views can report the same most-recent pending claim; assertions require that claim to be one of the two public submissions. Operator approval, author/mention verdict, award, lease recovery and reviewed-reward expiration guarantees are lost. No polling or alternate private worker is introduced.
- **Queue and Workflow:** the message-queue mixed case retains release of unconfirmed prompts and FIFO advancement/completion. Workflow's selected case uses actual heartbeat/claim sandbox tokens for failed then successful completion, reads both states through ordinary Run GET, and deletes the Workflow normally. Automatic time-budget control insertion/revocation and the1,000-credit worker-reviewed Workflow award are no longer asserted.
