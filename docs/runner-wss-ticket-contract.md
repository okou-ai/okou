# Direct Runner WSS tickets (#37025)

This is the API half of #36981. It does **not** provide a working WSS channel on its own. There is no ticket-issuance flag: after this API code is deployed, an authenticated owner may explicitly call bootstrap to obtain a ticket. Run startup does not issue tickets. The current Web does not call bootstrap, and the current Runner does not call consume or serve the new socket. Applying the additive database migration alone does not enable issuance. The internal target resolver from #37024 supplies a _candidate_ origin, not proof that DNS, TLS, Caddy, the Runner listener, or browser access work.

## Protocol contract for #37027 (Runner) and #37029 (Web)

1. An authenticated **Web session**, not a PAT or sandbox token, calls `POST /api/runs/:runId/wss/bootstrap`. The API authorizes the owner-scoped active Run and its current official Runner claim, matching fresh heartbeat, and validates the claimed hostname. A 200 response, always `Cache-Control: no-store`, is `{ "wssUrl": "wss://<claimed-hostname>:443/ws/<runner-uuid>", "ticket": "<43-character-base64url>", "expiresAt": "<ISO8601>" }`. The credential is never in the URL; the caller must not cache or log it. A missing, unowned, inactive or unresolvable Run returns generic 404.
2. Web opens exactly `wssUrl`. The **first application frame** is JSON `{ "runId": "<run-uuid>", "ticket": "<credential>" }` with no preceding Guest frames. The URL path fixes the destination Runner ID. Web sends neither auth cookies nor API tokens as WebSocket credentials. Web must wait for `auth.ok` before sending a Guest frame; it must discard the ticket on failure and obtain a _new_ one through bootstrap, never retry a consumed ticket and never fall back to an alternate host.
3. The Runner derives its canonical origin from its verified configured hostname (not from the first frame) and calls `POST /api/runners/wss/tickets/consume` with its **official Runner credential** and `{ runId, runnerId, origin, ticket }`. The `runnerId` must be the ID on the URL path. The API compares the SHA-256 digest, exact run, owner, Runner ID, canonical origin and 30-second expiration, rechecks current run ownership and target attribution, and atomically marks the ticket consumed. It returns `{runId, runnerId, orgId, userId, origin}` or generic 404. A PAT or non-official principal is rejected. Only the digest is stored; no raw ticket is logged or returned to the Runner after consumption.
4. **Mandatory Runner-side admission:** before `auth.ok`, look up `runId` in the destination process's _current local live Run-to-sandbox registry_, confirm the locally held Run is still attached to the official Runner ID and that the authenticated result matches, then bind this connection to the associated Guest stream (#37026). The API check is routing/authorization of a ticket, not proof of process-local possession; same-ID restarts and draining must be handled by the local check. No Guest frames before both checks. On run end, actively close streams; API ticket revocation alone only prevents _future_ redemption.
5. An authenticated owner may call `POST /api/runs/:runId/wss/revoke` to invalidate outstanding, unused tickets. Expiration, revocation, replay, a terminal or reattributed run, and an unavailable database all fail closed. The 30-second window is bound to the database clock. At most 16 unconsumed, unexpired tickets per Run are allowed. As an interim safeguard, issuance prunes at most 100 rows expired more than a day ago; this does **not** clean up rows when traffic stops. Independent scheduled cleanup is tracked in #37074.

**Threat boundary:** A ticket is a short-lived bearer credential bound to one run, owner, destination ID and hostname. The API does not cryptographically attest a physical browser device, nor can it distinguish the real browser from a thief who obtained an unused ticket and won the first redemption race. Device proof-of-possession would require a separate protocol design across API, Runner and Web; do not claim it from this first-frame ticket. The official Runner secret is shared across Runner processes, so API authentication does not itself attest which Runner process called consume; the destination-local Run registry check is indispensable.

## Staged rollout and WSS activation (outside this PR)

The API ticket schema and endpoints may be merged and deployed before their Web and Runner consumers. A session-authenticated owner can call bootstrap directly even without the Web adapter, creating a short-lived ticket and a digest row; issuance is not automatic on Run startup. The interim bounded pruning only runs on issuance; #37074 supplies independent retention cleanup afterward. This staged API availability is not a working direct WSS channel.

**Before activating Web-to-Runner WSS**, all serving official Runners, including draining processes with active Runs, must run the mandatory listener; pre-WSS Runs must drain; DNS, Caddy, TLS and browser reachability must be verified for every hostname tickets can select; the real non-production browser→Runner→Guest acceptance (#37030) must pass; #37074's independent cleanup must be deployed and verified; and separate production activation must be authorized. With no runtime issuance switch, any rollback to an old Runner or withdrawal of required ingress after Web starts using bootstrap needs a separately reviewed way to stop new client connections first. Already-issued tickets can still be redeemed until expiry unless revoked, and established streams require Runner-side closure. This PR makes no DNS, firewall, Caddy, listener or Web deployment change.
