# Staged host ingress for direct Runner WSS (#37028)

This slice stages a stable host Caddy service and the exact `/ws/<runner_id>` → `/run/okou-ws/<runner_id>.sock` route. It does **not** activate public ingress or prove the complete browser→Runner→Guest path. The claimed official Runner hostname from Ansible `inventory_hostname` is the **only** WSS DNS hostname; there is no second inventory→origin mapping, host registrar, endpoint lease or fallback. The API target resolver only produces an attribution-derived candidate. The API ticket endpoint already permits an authenticated owner to explicitly bootstrap a ticket **on demand**; #37025 has **no issuance flag**. A ticket alone does not make this channel available.

## Boundary and host staging

`ansible/playbooks/provision-runner.yml` owns the Runner's private socket-host prerequisites on every target host: the `okou-wss-caddy` group, `/run/okou-ws` as `root:okou-wss-caddy 0710`, and `/etc/tmpfiles.d/okou-wss.conf` to recreate that directory after reboot. It refuses unsafe pre-existing paths and does **not** install or start Caddy. Apply and verify this provisioning on each target host **before** deploying a Runner version whose listener requires the directory; changing the playbook alone does not prepare existing hosts. The normal host-provision action is hash-gated and only runs on hosts in workflows that invoke it; do not assume a preview or already-running host has been prepared.

`ansible/playbooks/stage-runner-wss-ingress.yml` must be run **only after provisioning and selecting a nonproduction host**. It requires the exact protected directory and tmpfiles configuration already in place, and remains separate from build, promotion and release automation. It stages Caddy files and a disabled, stopped unit, without enabling 443, touching DNS, acquiring a certificate, or restarting an existing Caddy service. It refuses missing opt-in, invalid/non-public-looking inventory hostnames, an active or boot-enabled `caddy.service` or `okou-wss-caddy.service`, an incorrect Caddy binary, a previously staged config for another hostname, foreign ingress files and unsafe existing directories. Passing the name syntax check does **not** prove the hostname belongs to us or resolves publicly. The operator must separately confirm the target is a nonproduction official Runner whose configured `hostname` is exactly the inventory name. Do **not** invoke this playbook on production without new authority; its opt-in is a safety catch, not an environment-discovery mechanism.

Install the **official Caddy v2.11.4** `/usr/bin/caddy` binary through an independently verified package/binary acquisition process; keep any default `caddy.service` stopped and disabled. Neither provisioning nor ingress staging invokes a package installer whose post-install hook could start a public listener. Review the contents and run on the chosen nonproduction inventory (example placeholders only):

```sh
cd ansible
ansible-playbook -i 'runner-staging.example.net,' playbooks/stage-runner-wss-ingress.yml \
  -e 'ansible_user=ubuntu wss_nonproduction_stage=true wss_acme_email=ops@example.net'
```

The dedicated `okou-wss-caddy` service is left **disabled and stopped**. Review the staged `/etc/okou-wss/Caddyfile`, `/etc/okou-wss/routes.caddy`, `/etc/systemd/system/okou-wss-caddy.service`, `/etc/tmpfiles.d/okou-wss.conf`, `systemctl is-active/is-enabled` for both Caddy units, and the expected filesystem owner/group/modes. `caddy adapt --validate` validates config only, not TLS issuance or live WebSocket routing. A *separately authorized* nonproduction activation requires an operator to establish DNS/certificate readiness and explicitly start the dedicated service. Do not use this playbook to edit a live ingress or restart it during Runner promotion. The service runs with a dedicated unprivileged user, `CAP_NET_BIND_SERVICE` only, a private persistent certificate store in `/var/lib/okou-wss-caddy/data`, and the Caddy admin endpoint off. Caddy automatic HTTPS uses a publicly trusted ACME issuer by default; it needs the verified DNS name and a viable ACME validation path (usually 443 for TLS-ALPN; an HTTP challenge may need port 80). No host certificate or firewall rule is provisioned by this PR. Caddy may open its own validation listener when **separately started**; inspect the concrete network policy before that step.

## Protected socket interface (#37027)

The host directory `/run/okou-ws` is **root:okou-wss-caddy 0710**. The dedicated Caddy user has traversal only, not directory write/list permission; Runner service processes currently run as root. A WSS-capable Runner must bind only `/run/okou-ws/<its lowercase-hyphenated-UUID>.sock`, then set socket **root:okou-wss-caddy 0660** *before* reporting healthy/claiming. The pinned route requires **both** an anchored UUID match on Caddy's decoded path and an anchored match on the original raw request target: Caddy's path matcher alone normalizes percent-encoded IDs and doubled slashes. No encoded alias, query or traversal selects a socket. It has one dynamic Unix upstream and a 404 catch-all. Caddy matches the path, not the run; the first-message ticket and process-local live-run admission are mandatory in #37027. An ordinary HTTP request on an exact path is forwarded; **the Runner must reject it**, not Caddy's matcher. Missing sockets fail without redirecting to another process. Versioned Runner IDs coexist under the same static Caddy config while an old process soft-drains. A sequential same-ID restart may bind only after its old process stops and safely relinquishes its socket. The Runner must reject unsafe/symlinked paths, collisions, and ownership changes, and must never unlink another process's socket; the host playbook does not remove sockets. `/etc/tmpfiles.d/okou-wss.conf` restores only the directory after reboot; it is installed by Runner host provisioning, not by ingress staging. Coordinate group/mode and service startup order with #37027; no claim is made that the not-yet-merged Runner listener meets the contract today.

## Verification checklist before any Web activation

For **every** official hostname that current ticket target resolution could select, including a draining old process with active Runs, record a dated per-host receipt (hostname, Runner IDs with active Runs, observed DNS answers, TLS certificate identity/expiry/trust, Caddy version/config hash, exact socket probe and result). Do not substitute a sampled host, heartbeat, hostname syntax or `adapt` output for these checks:

1. Verify Ansible `inventory_hostname` equals the configured Runner `hostname`, the winning `agent_runs.runner_hostname` and the exact browser-facing name. Obtain DNS-only A/AAAA records for this name (no CDN proxy/origin-only cert), match **all** address answers to the intended host, and check both IPv4 and IPv6 when published. Do not repoint an old name/IP/cert while any of that host's Runs are still active.
2. With the intended nonproduction service separately activated, verify TCP 443, the exact SNI/hostname and full certificate chain using a normal browser trust store. Inspect expiry and Caddy renewal logs (`journalctl -u okou-wss-caddy.service`) and persisted Caddy data across a process restart/reboot. A Cloudflare Origin CA certificate is not browser-trusted on a DNS-only direct WSS origin. Alert on renewal failures/expiry, DNS drift, service health and socket handshake errors; recheck after renewal. `openssl s_client -connect <host>:443 -servername <host> -verify_hostname <host> -verify_return_error` helps diagnose the chain but is **not** proof of browser trust or public network reachability alone.
3. Verify real WSS HTTP/1.1 Upgrade over TLS using a disposable socket/test Runner on that **exact** host and path, a wrong/missing Runner ID, malformed/traversal path, ordinary HTTP rejection by the Runner, and two distinct release IDs. Include old-release reconnect during soft drain and a Caddy restart/disconnect/reconnect using a fresh ticket once #37027 is available. Do not put tickets in URL, query or logs. The local executable test `CADDY_BIN=/path/to/caddy python3 ansible/tests/test_runner_wss_caddy.py` validates the route with synthetic Unix test sockets and locally trusted test TLS, **not** external DNS/ACME or the real Runner. A local Caddy v2.11.4 ALPN-h2 probe did **not** receive `SETTINGS_ENABLE_CONNECT_PROTOCOL` and its attempted HTTP/2 WebSocket extended CONNECT was reset with `PROTOCOL_ERROR` before reaching the test socket; do not claim that transport is supported by this pinned setup. Browser fallback to HTTP/1.1, and HTTP/3 behavior where advertised/supported, still require real browser/Caddy/Runner verification in #37030. An HTTP/1.1 test or config validation does not prove either variant.
4. Before wiring Web to bootstrap, verify every serving official Runner (including draining processes with live Runs) has the mandatory, fatal-on-failure listener, pre-WSS Runs are drained, per-host ingress receipts pass, and #37030 completes nonproduction browser→Guest acceptance. #37074's independent retention cleanup is a separate activation prerequisite tracked by the parent; this PR does not work on it. A single unverified ticket-selectable host means **no fleet-wide Web activation** without a separately reviewed selective eligibility gate. No public DNS/firewall/production Caddy activation or release is authorized here.

## Changes and rollback

Promotion of a WSS-capable Runner must bind and pass its own listener/doctor gate **before** draining the old Runner. Promotion adds/removes sockets; it must never regenerate/reload Caddy for each release. A failed new listener must abort promotion while the previous healthy Runner continues. Caddy restart/reload is separate and may drop established WSS; clients must obtain a new ticket and reconnect to the original owning host (no alternate host). Host replacement keeps old DNS/IP/cert/Caddy and its draining sockets until its Runs complete; configure and verify the replacement hostname independently before selecting it.

If ingress fails after activation, TLS/Caddy or socket connection fails closed; it never authorizes attachment elsewhere. The current API can still issue an unusable short-lived ticket when an owner explicitly calls bootstrap. **There is no `OKOU_WSS_TICKET_ISSUANCE_ENABLED` flag to turn off.** Before rollback to a pre-WSS Runner or withdrawal of public ingress *after Web has begun using bootstrap*, design and review a way to stop new client connection attempts and handle already-issued tickets/established streams. Disabling Web calls alone does not disable direct owner API bootstrap. Fleet rollback and production activation require separate authorization; don't claim that a Caddy stop is a safe issuance switch.
