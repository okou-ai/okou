# Pi inference lifecycle foundation

Refs #34242, foundation of #34236 and its [Phase A contract](https://github.com/vm0-ai/vm0/issues/34236#issuecomment-5674625513).

The foundation installed additive storage and compatible readers. #34244 adds the first producer for that contract without changing its schema. The producer is selected only for eligible Pi chat starts when the org-scoped `piDeferredSandbox` switch is enabled; the switch still defaults off for everyone, including staff. Readers and recovery never consult the switch, so disabling new starts does not strand an admitted v4 Run.

The epic measures original server API start to the start of the first actual provider HTTP span, not TTFT. The 250 ms critical path plus 50 ms headroom remains a design budget. This implementation adds correlation timing but makes no latency, deployment, activation or production benchmark claim.

## Default-off durable API producer

Eligible starts branch before persisted environment-secret decryption, complete Runner payload construction, Sandbox admission and job publication. They retain the existing authorization, queue-first input claim, official-workflow catalog, credit, personal-subscription and compute-erasure admission owners. Legacy recomputation is limited to two explicit compatibility boundaries: an unsupported historical H0 representation for which durable capture returns no H0, or persisted Storage mounts that fail the retained `storageMounts` schema. Once both representations are supported, every other context, resource, or identity invariant fails the launch instead of silently falling back.

The producer captures the exact selected route, model-visible resource snapshot, memory recall, canonical H0, session identity and original `api_started_at`. Once deterministic object hashes exist, speculative SDK input preparation overlaps immutable configuration/context publication, the KMS-encrypted activation credential object (whose deferred body-secret payload may be empty), and subscription admission. One transaction then writes the canonical Run/session/input claim, v4 inference row, reference edges, usage allowance and existing memory-stage request. A committed winner schedules its durable dispatch immediately after the transaction; request cancellation does not revoke that owner.

Immediately before provider transport, the lifecycle transaction changes `ready/not-started` to `provider/may-have-started` for the same epoch and stable attempt ID. The transaction resolves before the runtime transport marker can permit HTTP. A direct answer persists usage, H1, public events and the normal checkpoint/completion without creating a Sandbox intent, lease, Runner job or notification. Pending tools, accepted active input or an explicit pre-provider fallback call the existing durable demand publisher; only accepted demand can create consumer work.

Maintenance recovery claims an expired owner under the same lifecycle lock and advances the common epoch. `ready/not-started` decrypts only the retained narrow API activation snapshot, revalidates its exact credential source at the ordinary provider boundary, and dispatches one attempt without constructing a Runner payload or taking Sandbox capacity. `publishing/settled` reads the retained H1 producer receipt, idempotently settles any missing usage, and resumes only local publication. `provider/may-have-started` terminalizes truthfully and never resets or replays H0. Canonical terminal transition advances the epoch again, so a recovered uncertain attempt moves from epoch 1 to recovery epoch 2 and terminal fence 3; stale owners cannot publish.

Launch snapshot version **4**, inference input/contract version **1**, the selected Pi provider/model generation and H1 `manifestGeneration` are independent domains. One advancing does not imply another advanced. `inputGeneration` is the existing canonical input claim generation; it is not a new product sequence.

Hash references bind immutable objects under the captured run's org/user namespace. The producer and consumer implement verified publication, exact input capture and live-reference retention. They do not put durable H0/H1/input/secrets into the existing short-lived `pi-api-first-turn` staging cleanup namespace or treat a resource-cache TTL as ownership. Source conversation retention also retains its existing blob reference; no second blob count is incremented or decremented for the same conversation. Newly published context/H1/secret objects have explicit Run reference edges and a cleanup owner. Objects written before a failed DB commit remain unreferenced cleanup work. Deferred secret expiry produces an explicit terminal/preparation error; recovery never silently selects new credentials or an empty secret bundle.

## Durable ownership and transitions

All new rows use the existing run ID as their primary key. `agent_run_sandbox_intent` is the unique outbox; notification receipt is diagnostic progress, not execution authority. The old `agent_run_queue` and `runner_job_queue` remain full-launch records. A no-job inference row is identified by v4, never by absence of a job.

`owner_epoch` is one common monotonically increasing execution fence across inference, intent and any active lease. A handoff/reclaim changes the common epoch atomically under the run lock. An intent also has a positive `generation` to distinguish a recreated execution demand. Every future materializer/Runner publication must prove both generation and current epoch. A lease/intent epoch different from inference is invalid. The foundation's run-local CAS predicate proves current epoch, nonterminal phase and unexpired API ownership; Sandbox owners additionally use their phase deadline and generation, never the expired API deadline.

| Phase / public status                 | Owner and durable precondition                                                                                                                                | Deadline / legal next transition                                                                                                                                |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `admitted` / pending                  | Run and immutable input committed; activation false; stable first `provider_attempt_id`; attempt `not-started`; no intent/lease                               | Bounded inference `deadline_at`; readiness may become `ready`, or terminal                                                                                      |
| `ready` / pending                     | Activation true only after canonical admission, permission, captured source, credit and independent inference protection succeed; attempt still `not-started` | API deadline; atomically commit `provider` before any possible external send, or explicit untouched-H0 Sandbox-first demand                                     |
| `provider` / pending                  | Current epoch; activation true; `may-have-started` committed before the request could have external effects                                                   | API deadline; save durable H1/publication receipt and settle attempt, or terminal with truthful uncertainty                                                     |
| `publishing` / pending                | Attempt `settled`, verified durable publication receipt; no intent or lease                                                                                   | API publication deadline; idempotently write canonical output/checkpoint/usage then complete, or atomically publish matching H1 plus Sandbox intent             |
| `sandbox_waiting` / pending           | Unique waiting intent; matching common epoch; exact H1 or explicitly untouched H0; no active lease                                                            | `expires_at`, greater than demand `enqueued_at` and at most **2 hours** later; reserve/prepare, cancel or expire                                                |
| `sandbox_preparing` / pending         | Intent preparing; lease reserved/preparing; matching epoch; materializer attempts tracked                                                                     | Minimum of queue expiry, explicit attempt deadline and lease deadline; build outside transaction, publish ready only with a current fence, or reconcile/release |
| `sandbox_ready` / pending             | Intent ready; lease ready; complete compatible job and durable redeliverable demand                                                                           | Explicit claim deadline on lease; Runner claim checks generation/epoch; no fake heartbeat                                                                       |
| `sandbox_running` / running           | Intent and lease claimed; actual Runner identity; common epoch                                                                                                | Actual execution deadline on lease plus existing real Runner heartbeat policy; checkpoint/complete/cancel/timeout                                               |
| `terminal` / existing terminal status | Canonical completed/failed/cancelled/timeout transition won once; inference epoch advanced, intent fenced; attempt and usage facts preserved                  | No new provider/materializer/job publication. Unreleased lease becomes releasing and continues to count until release evidence exists.                          |

Current legacy reference limits are 5-minute pending-start, 2-minute running heartbeat and 2-hour queued demand. The waiting deadline is separate from the 45/55-second API coordination window. Producer and consumer set bounded API/publication/materialization/claim/execution deadlines at their actual phase starts. Queue promotion mints fresh signed URLs from captured references. Original `api_started_at` never changes on wait, recovery, promotion, claim, retry or cleanup.

Recovery is explicit:

- A committed ready/not-started owner can be claimed with a new epoch before transport; an expired owner has no authority.
- `may-have-started` means unknown external effects even if no response exists. A crash, timeout or local cancellation never resets it to not-started and never authorizes automatic replay. Only supported provider evidence can reconcile it; otherwise publish a truthful uncertain/failure outcome and preserve usage reconciliation responsibility.
- A settled H1 resumes usage and local publication/checkpoint work. H1 is retained before the usage marker, so a crash after provider success can replay the response-derived idempotent ledger write without rerunning inference. Existing last-event sequence, run usage identity and checkpoint uniqueness provide the canonical idempotency boundaries; `published_sequence` records acknowledged local progress.
- Pending-tool H1 preserves original tool IDs; settled-session H1 permits only eligible active-input continuation. Untouched H0 is allowed only when provider attempt is still not-started. An API result cannot be replaced with H0.
- Lost or duplicate notification redispatches the same intent. A stale materializer may clean up its own uncommitted artifacts but cannot publish a job. A duplicate Runner claim cannot acquire a second lease.
- Expiry/cancellation fences ownership. Lease expiry alone never proves that a remote Sandbox stopped. Only verified stopped/unclaimed cleanup evidence permits `released`; the nonempty `release_evidence` field records that fact. No release reconciler is introduced in this foundation.

## Capacity, permissions and lock order

For an organization, count each run once if it has a lease in `reserved`, `preparing`, `ready`, `claimed` or `releasing`, **or** is a legacy full-launch pending/running reservation under the existing conservative pending-activity policy. A UNION of indexed legacy reservation IDs and indexed active-lease IDs prevents double counting without scanning every retained run in the organization. New API-only and waiting runs consume zero Sandbox slots. Terminal runs with uncertain cleanup still count. `released` requires evidence and consumes zero. An empty legacy queue is not evidence of zero running/reserved capacity.

Both organization admission and member-facing active usage use this formula. Legacy queue/orphan readers and legacy Runner claim explicitly exclude v4. #34243 must supply the generation/lease-aware consumer before #34244 emits new demand; simply removing that exclusion is not a compatible activation.

Independent inference start/in-flight protection serializes provider and organization counts with database advisory locks and rejects excess with typed retryable `429 PI_INFERENCE_BUSY`, without queuing behind Sandbox capacity. `PI_INFERENCE_ORG_MAX_IN_FLIGHT` defaults to 8 and `PI_INFERENCE_PROVIDER_MAX_IN_FLIGHT` defaults to 128; both are positive deployment configuration, independent of Sandbox capacity and customer concurrency. Admitted/ready/provider/publishing rows hold a reservation. A terminal `may-have-started` attempt retains it for the 55-second coordination grace even if local usage settles, because transport abort does not prove the remote effect stopped; this bounds ambiguity without leaking capacity forever. Existing credit/catalog/provider consistency locks remain necessary. A credit-admitted pending v4 run retains existing billing semantics, including personal subscription eligibility; Sandbox slots and tool/model charges remain separate authorities.

| Operation                       | Required lock order / boundary                                                                                                                                                                                                                                                                   |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Existing request admission      | Existing source validation, catalog definition publication and credit admission ordering remain unchanged. Capture exact configuration/source before provider send. Preserve catalog/credit locks until their own successor contract proves removal safe.                                        |
| API ownership CAS               | Existing parent thread/session lifecycle locks when applicable, then run row, then inference row. **No organization Sandbox-capacity advisory lock.** No provider HTTP, object I/O or materialization in the transaction.                                                                        |
| Canonical checkpoint/completion | Existing per-run checkpoint lifecycle advisory lock, thread lock, run row, existing memory/storage locks, then canonical references/blob writes; terminal credential cleanup follows the existing provider order.                                                                                |
| Hard cancellation/timeout       | Existing thread/session-before-run path, then inference, intent, lease; terminal transition and epoch fence commit together. Provider coordination remains after lifecycle locks. Remote cancel occurs after commit.                                                                             |
| Sandbox capacity reservation    | Existing org capacity admission authority before run/intent/lease mutations; never acquire this lock while already holding a run row. Atomically count and reserve. Build remotely after commit; reacquire canonical lifecycle locks and verify the fence before publishing.                     |
| Source retention/erasure        | Parent thread/session locks, target runs in stable ID order, inference/intent/lease and conversation references, then storage/blob release last. The producer validates the captured thread/session snapshot and commits its H0 FK under this order. Never acquire parent rows after blob locks. |

The lifecycle fixture holds the real capacity advisory lock in one database connection while another completes the run-local owner CAS. The producer behavior test additionally holds that same capacity key across chat creation until intercepted provider HTTP begins, and verifies that no intent, lease or job exists. These tests prove database-boundary independence, not production latency or remote Sandbox behavior. Existing personal-account tests cover ordinary disconnect retention with `PersonalSubscriptionPriority` enabled and hard user/org/membership authority removal in legacy, API-only and waiting states. No token/account fallback is introduced.

FKs: inference run -> run CASCADE; intent -> inference CASCADE; lease -> intent **RESTRICT**; H0 source -> conversation **RESTRICT**. RESTRICT prevents parent cascades from erasing unknown capacity/source ownership. A referenced source cannot be deleted behind another admitted run. Hard external authorization is revoked even when resource/usage erasure must finish later. Production activation requires the account-erasure and Sandbox cleanup owners to reconcile these bounded conflicts; this foundation installs no external reconciler.

## Migration, scale and deployment

Drizzle generates the schema SQL, journal and snapshots. The generated expand SQL is edited only in its new, unshipped SQL file to replace the launch CHECK as `NOT VALID`; a separately generated custom migration validates it. No historical launch record is rewritten and no row backfill is required.

1. `1134_pi_inference_lifecycle`: create the three empty sparse tables, foreign keys and indexes; replace the launch CHECK in one transaction. The replacement still accepts every old NULL/v1/v2/v3 write and enforces the exact v4 shape on every new write. `NOT VALID` avoids a historical scan while holding the expand transaction's exclusive table lock. PostgreSQL still needs relation locks for CHECK replacement and FK setup.
2. `1135_validate_pi_inference_launch`: validate the expanded CHECK in its own transaction using `SET LOCAL statement_timeout = '30s'`. The repository default `lock_timeout = '1s'` still applies. Validation scans `agent_runs` under PostgreSQL's validation lock; normal row writes remain legal. Final catalog state is validated and matches the generated schema snapshot.
3. The expand migration keeps default 1-second lock / 10-second statement timeouts. Failure rolls back the whole expand transaction and journal. Validation failure leaves the committed additive schema enforcing writes, rolls back only validation/journal, and blocks release progression until an explicit later retry succeeds. A timeout is not permission to raise production limits or bypass checks.

Refreshed read-only MaskDB aggregate receipts (2026-09-15 UTC): `agent_runs` **282,839** at **05:18:20**; `agent_sessions` **71,954** at **05:18:19**; `conversations` **277,397** at **05:17:54**. The additional conversation census covers the final H0 FK scope. Controller receipt at 04:48:40–42 had runs 282,777, sessions 71,937, legacy queues zero each and running 20. These independent aggregates are not a frozen cohort, physical table measurement or production lock-duration evidence. Reproduce through the live `vm0-prod-ro` structured aggregate gateway: `{"table":"agent_runs","metrics":[{"op":"count","as":"row_count"}],"limit":10}`, substituting other names. No rows/secrets or production writes are needed.

The migration validator builds the real pre-expansion schema in an isolated PostgreSQL database and uses synthetic metadata at the refreshed retained-table counts. It tests an actual competing relation lock, expand rollback, injected validation journal failure, retry, old/new writes, unchanged historical records and no automatic lifecycle rows. Bounded `EXPLAIN (ANALYZE, FORMAT JSON)` claims/deadline queries use phase/state plus deadline/enqueue and run-ID indexes. Source FK lookup has its own index; run-keyed reader/capacity joins use primary keys. Sparse-table cardinality and production contention will differ; local plans/timings are representative validation, not production acceptance.

## Validation boundary

Focused producer behavior uses the real chat creation boundary, PostgreSQL lifecycle rows and intercepted provider HTTP. It verifies provider start while the real Sandbox-capacity lock is held; the committed uncertainty fence before transport; direct completion with idempotent usage and zero intent/job/lease; typed organization and cross-organization provider overload before a second attempt; ready-owner recovery from the narrow retained activation snapshot with one fresh fenced request; terminal rejection after that captured model source disappears, with no request or demand; untouched-H0 demand for native input with no provider request; settled-H1 demand for one input committed during provider execution; settled-H1 publication plus missing-usage recovery with no request; uncertain-provider terminal fencing with no H0 replay; and one H1 tool handoff through the accepted consumer, Runner claim, cancellation and release route. Existing lifecycle/consumer tests retain jobless cancellation, expiry, common epochs, capacity, erasure, account and physical-release coverage. Legacy API-first tests and CI remain the broader regression boundary.

No production activation, remote Sandbox/provider end-to-end, production migration timing, provider-start benchmark, release acceptance or sub-300 ms result is implemented or claimed here. The switch remains default off. Those are separate controller/release responsibilities, not evidence supplied by green CI. Keep #34236 open for whole-epic acceptance.
