# WSS target resolution (API-only prerequisite)

The API resolver in `turbo/apps/api/src/signals/services/runner-wss-target.service.ts` is an **internal, read-only prerequisite** for #37025. It never issues a ticket or returns a browser URL. Its result explicitly marks `ingressVerification: "not-observed"`; neither its result nor a Runner heartbeat proves that DNS, TLS, Caddy or the Unix listener is currently reachable. #37027 must reject a ticket for a run absent from that process's live run-to-sandbox registry, including after a same-ID restart.

The service requires the owner's organization and user ID, an `agent_runs` row with `status=running`, its `active_agent_runs` row, winning official Runner attribution, a matching `runner_state` group and a heartbeat in the last 30 seconds. Both `running` and `draining` Runner modes can serve **already owned** runs; `starting` and `stopping` cannot. A heartbeat can temporarily outlive a dead Runner, so a selected target is not authorization. No WSS-specific heartbeat-generation comparison is made. Claims without winning official Runner identity or a usable hostname remain ineligible; a claimed release number is diagnostic, not a capability check.

The official Runner's Ansible-configured `inventory_hostname` is the intended browser-facing WSS DNS name. The resolver rejects malformed hostnames, IP literals (including abbreviated/hex/octal forms normalized by browser URL parsers) and known local/reserved suffixes, then constructs `wss://<runner_hostname>:443` from a canonical lowercase, multi-label DNS name without a second hostname-to-origin mapping. A syntactically accepted name may still be privately resolved, misconfigured or unreachable; this check does not establish public DNS ownership or reachability. The hostname is **not** a credential or a reachability proof; only an authenticated official Runner can claim the run, and the eventual destination Runner must independently authorize the currently live run. When replacing a host, keep its old DNS/IP/certificate pointed to that host until its runs drain; never silently repoint a still-serving name.

There is no API-side Runner version floor or WSS capability check in this resolver. It may return a hostname-derived candidate for an older Runner during a mixed-version rollout, so consumers must never treat a resolved target as evidence that the listener exists. #37027 makes WSS listener bind/supervision mandatory before a Runner is healthy or claims work. #37025 must keep ticket issuance off until **every serving official Runner, including any draining process with an active Run**, has the mandatory listener **and** all Runs owned by pre-WSS Runners have finished. An older process that could still claim work is not ready just because it has no active Runs. Promotion and rollback must preserve that fleet-wide condition: disable issuance before allowing an older Runner to serve Runs again.

#37028 must separately verify DNS-only address, browser-trusted TLS and Caddy routing **for every hostname that ticket issuance could select** before #37025 enables tickets. There is no per-host mapping/allowlist to activate some hosts implicitly; if any eligible host is not ready, keep ticket issuance off or establish a separately reviewed eligibility gate in #37025. #37030 validates the real non-production browser→Caddy→Runner→Guest path before any production activation. This resolver has no public route, DB migration, host identity credential, sidecar registrar or readiness lease. Because #37025 has not yet exposed authenticated bootstrap, its DB-backed integration tests use the existing gated `/api/test/runtime-state/action` support route to read this internal resolver after creating real Runs/claims/heartbeats through the API; production clients cannot call that test route. Database failures propagate rather than being converted into an absent target.
