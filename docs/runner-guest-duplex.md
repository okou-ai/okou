# Private run-scoped Guest duplex (#37026)

This is **not a public endpoint or a product message protocol**. #37027 owns ticket redemption, first-frame WSS admission, required listener startup/health and downstream forwarding. #37030 owns real browser/Caddy/Guest acceptance. This slice neither enables ticket issuance nor authorizes production ingress.

## Attachment contract for #37027

The owning Runner creates one `runner_remote::guest_duplex::RunGuestChannels` instance in `ExecutorConfig`. The executor registers the exact `ExecutionContext.run_id` only while it holds that run's prepared sandbox; it drops the registration before sandbox cleanup, park and reuse. #37027 must share **that same instance** with its listener. After redeeming a ticket, call `open(exact_run_id)` and require success **before** sending `auth.ok`. Never create a second registry, consult status.json/DB, infer a sandbox from the socket path or accept a client-supplied sandbox ID. A missing run, unavailable Guest candidate, full run, cancelled run, mismatched provider sandbox ID or prior execution epoch returns an error. The listener must close its WSS stream on `Channel::cancelled()` or retain `Channel::cancellation()` before splitting and select `ChannelCancellation::cancelled()` independently of both IO halves; drop the halves when it fires; run completion/revocation must not keep an operation reservation alive. An error from `send`, `recv` or `finish_send` closes that WSS stream, never resumes parsing a partial frame. #37027 independently remains fatal on WSS bind/accept-loop failure; Guest transport errors fail individual attachments closed.

`Channel::split()` gives independent Sender/Receiver ownership for forwarding in two directions; the caller keeps the cancellation observer separately. Each send carries one opaque binary frame of at most 64 KiB; no JSON, routing, chat receipts, SSH/VNC or exec content is interpreted. Send/recv ordering is per direction within one stream; unrelated streams have no cross-stream ordering. `Sender::finish()` half-closes host→Guest while receiving can continue. Guest EOF yields `None`; malformed/oversized/partial frames return errors and poison only that stream. Dropping both halves releases the per-run permit and the provider's normal-operation reservation. A run permits at most eight concurrent streams. No unbounded task or application queue is created: synchronous framed writes respect Unix/vsock backpressure, a frame is limited to 64 KiB, the Guest holds at most eight workers plus one pending connection, and each private accept, Guest-control lookup and activation stage has a two-second timeout. #37027 must impose its own overall admission deadline.

## Dedicated Guest ingress and same-artifact lifecycle

Runner and Guest binaries ship in the same Runner artifact. During rollout, a draining Runner keeps executing its own Runs on its own sandboxes; new Runners do not inherit old Guests. No cross-version Runner/Guest protocol negotiation or fallback is required (see [deployment compatibility](deployment-compatibility.md#what-requires-compatibility)).

Firecracker binds a dedicated private 0600 Guest duplex listener on **52002** under its validated per-sandbox 0700 runtime directory. Guest control uses **52000** and the unchanged one-operation Guest RPC listener uses **52001**. Duplex does not enter the RPC decoder, classifier or accept queue; independent listeners share only the sandbox's current-run and normal-operation reservation authority. Each duplex connection is a separate long-lived stream with its own framing and lifetime, not the one-shot RPC terminal/15-minute helper contract. Separating listeners does not itself improve data throughput or grant authorization.

Only the Guest initiates a duplex connection. The host reserves its single pending queue slot and replies `READY` (2): this acknowledges capacity, **not authorization**. The Guest bounds the wait for `READY` to five seconds, then waits without a timeout for actual activation; an unresponsive ingress or rejected candidate closes this attempt and the Guest retries privately. **The idle candidate does not hold a normal-operation reservation and cannot block park.** On `open`, the provider checks the exact current `ParkCoordinator` run binding, acquires the reservation, then sends `ACTIVATE` (1). Park/termination/runtime exit cancels both protocols' operations; each endpoint is dropped/rebound across park/unpark, never looked up from a reused sandbox cache. A duplex-only listener failure revokes its streams without cancelling otherwise healthy RPC work. `guest-init` starts its independent private duplex worker alongside the 52000 control service in its existing PID 2 child; it maintains one pending connection with a bounded five-second ingress acknowledgement wait, at most eight active echo workers and no business consumer. The acknowledgement timeout is removed from the socket before waiting for activation so an idle pending or established stream can remain idle. If the Guest worker is unavailable, `open` fails closed; this is an availability boundary, not a mixed-version compatibility path. Rebuild and validate the paired Runner/Guest image in #37030's integrated path before any rollout gate is lifted. No `OKOU_WSS_TICKET_ISSUANCE_ENABLED` setting is assumed.
