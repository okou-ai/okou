# Okou Browser extension

The first-party MV3 extension owns source-window consolidation and native window/tab control. The portable CDP client/protocol lives in `@okouai/browser-extension-client`. The worker and client have independent connection/session lifetimes; disposing a client never closes user tabs or windows.

A declarative stylesheet supplements only default document fonts. Its first normal cascade layer contains zero-specificity root rules: Chrome's standard family (`-webkit-body`) remains first, followed by private Noto Sans (including Devanagari) and all four regional CJK faces. Root languages `ja`/`ko` prioritize JP/KR; `zh-Hant` and `zh-TW/HK/MO` prioritize TC; other roots prioritize SC. Remaining regions follow in SC/TC/JP/KR order. Every chain retains all sources, so English or Chinese documents can reach Korean glyphs and TC/JP/KR documents can reach simplified Han missing from their preferred face. Descendants inherit this chain; their language alone does not reorder shared Han regional typography. The private aliases preserve website family names. The standard preference can differ from `serif`; this does not replace it with a generic serif choice. Website font declarations, layers, variables, shorthands and live states keep control through the native cascade. Both metadata and root CSS load at document start in matching HTTP(S) documents and frames, including matching blank frames.

Only six reviewed FontFace declarations are bundled in `public/noto-fonts.css`: regular/italic Noto Sans and regular SC/TC/JP/KR. Versioned complete WOFF2 files load from Google Fonts (`fonts.gstatic.com`) with `font-display: swap`; no particular system font installation is required. Complete CJK files cost about 2–4 MB on first use, and the browser synthesizes additional weights/CJK oblique styles. A small full-face set avoids hundreds of CSP violations from segmented declarations on restrictive pages. The page's `font-src` policy and ordinary network availability still apply: denial/unavailability retains native fallback and may report the small declared set. Remote requests inherit browser request/referrer policy; asynchronous swapping and caching are browser-owned, without a cross-origin cache guarantee.

A glyph supplied by the standard face does not need the Noto tail, but this is not a promise to avoid downloads whenever any OS fallback can draw it. Non-Korean faces exclude Hangul blocks so Korean-only text reaches KR without first downloading SC/TC/JP. Other coverage hints keep unrelated scripts from downloading a full CJK file; the binaries themselves remain complete. Mixed text may need several complete files, increasing aggregate first-use transfer. Noto may replace healthy system fallback for default non-Latin text, changing appearance or wrapping.

This intentionally does not append a fallback to authored font stacks or replace UA control/code fonts. Text and shadow content that inherit the document default can use the supplement; their own explicit fonts remain authored. Incomplete Noto coverage, explicit website stacks, embedded document fonts, raster canvas/images and browser chrome are not guaranteed repaired. No page text/control values are inspected or sent to a `text=` API, no website stylesheet or CSP is rewritten/reloaded, and no font-specific runtime JavaScript, observer, new hosting or extra permission is used.

Font versions and metadata/source hashes are pinned in `public/noto-fonts.css`. Update them together from Google's official full-WOFF2 metadata and verify actual script coverage, standard/author precedence and policy overhead before release. The metadata format was requested with Firefox/40.0 to obtain unsplit static sources; this does not override the runtime browser's identity. Builds/releases use the reviewed declarations without contacting the CSS API. No font binaries or generation tool/dependency are added. Noto is open source; licensing and service details are in [Google Fonts' FAQ](https://developers.google.com/fonts/faq).

From this directory:

Packaging requires `zip` and `unzip`. Release-boundary tests also use `yq`; CI runs these commands on the standard Ubuntu runner.

- `pnpm build` builds the worker and deterministic ZIP/checksum/source provenance under `artifacts/`.
- `pnpm test` runs the owned full-Chromium scenarios against loopback fixtures, one worker at a time. Set `CHROMIUM_EXECUTABLE` to select an installed full Chromium. Headless Shell cannot load extensions.
- `pnpm verify-package` checks ZIP contents and repeatability across timezones.
- `pnpm check-types` and `pnpm lint` use the shared workspace conventions.

CI uses an `ubuntu-latest` job for release-boundary tests, the production build and deterministic ZIP verification. It transfers the verified `dist` by exact artifact ID to `test-browser-extension`, whose job container uses the official Playwright Noble image pinned by version and digest in `.github/workflows/turbo.yml`. The image preinstalls full Chromium, system libraries and the local fonts used by the glyph-selection tests, independently of the `ubuntu-latest` host. The native job installs the locked JS dependencies and runs Playwright against that build without apt, browser installation or packaging tools. Update the image version and digest together with this package's `@playwright/test` version.

The manifest and package version are managed together by release-please. Production publication packages the immutable release source and uploads it to Browser Use before API deployment. When the release includes an extension, API deploys with that exact upload's ID. Without an extension release, the shared API deployment environment action queries Browser Use and selects the highest numeric `Okou Browser` version across all pages. Preview/staging API deployments use the same lookup. Missing extensions, ambiguous highest versions and provider failures stop deployment.

The resolved UUID is pinned in the API deployment's required `OKOU_BROWSER_USE_EXTENSION_ID` environment setting. It is not read from or persisted to a GitHub Variable. Every new managed Browser installs that deployment's selected extension; an existing Browser retains its installed ZIP until normal instance replacement. The provider upload UUID differs from Chromium's runtime ID. Future uploaded versions must remain compatible with supported API consumers.

Release commands run from the repository root. Publication takes `RELEASE_TARGET`, `BROWSER_EXTENSION_VERSION` and `BROWSER_EXTENSION_TAG`; credentials come from `GH_TOKEN` and `OKOU_BROWSER_USE_API_KEY`. It reads the package's `artifacts/` directory, preserves immutable artifacts and upload-attempt/completion receipts, and writes the verified `extension_id` to `GITHUB_OUTPUT`. A publication failure blocks that release's API deployment; an uncertain upload must be reconciled before rerunning.

The deployment resolver takes `BROWSER_EXTENSION_RELEASE_CREATED` (defaults to `false`). When `true`, `BROWSER_EXTENSION_ID` must be the valid UUID from this release's publication; lookup is not substituted for a missing output. Otherwise it uses `OKOU_BROWSER_USE_API_KEY` to list extensions and compare their stable `x.y.z` release versions numerically. It prints only the selected UUID to stdout and exits nonzero on failure. API runtime does not query the extension registry.

After saving the verified upload receipt, publication keeps the newest five numeric `Okou Browser` versions in Browser Use and deletes older uploads. Cleanup runs only in the new-extension publication flow; ordinary API-only, preview and staging deployments do not delete extensions. Other project extensions and immutable GitHub release assets are preserved. Existing browsers keep their installed extension, but an API deployment pinned to a deleted UUID can no longer create new browsers with that ID.

The release retains the ZIP, checksum, source provenance, upload attempt and completed upload receipt as immutable GitHub release assets. A rerun reuses a matching completed upload and resumes cleanup from the current registry inventory. Cleanup failures stop publication without uploading a second copy on retry. If an attempt has no completion receipt, reconcile the provider outcome before rerunning; the publisher refuses to create a second upload.

For explicitly authorized provider verification, `pnpm test:provider` uses `OKOU_BROWSER_USE_API_KEY` to upload a disposable artifact, create its own Browser, validate bridge/routing/worker behavior, and clean up those resources. It does not use an existing Browser or change live configuration. PR CI runs local Chromium and controlled provider-boundary fixtures instead.
