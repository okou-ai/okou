## Transcription rules

Cases are selected from `reconciliation.tsv`. Keep each ID, the Vitest full name and mode from `baseline.json`. Encode the full name as a JSON string on the `Vitest` line so whitespace and control characters round-trip. Vitest can truncate interpolated titles, and 33 expanded rows share a title with another row in the same file. Preserve the source parameter in the Given when the runtime title is ambiguous. Prettier collapses runs of spaces in Markdown, so a full name with repeated spaces keeps them as `\u0020` JSON escapes on the `Vitest` line; the decoded name is byte-identical to the runtime name. Follow imported `.suite.ts` and `.cases.ts` registrations and their helpers when the entry file delegates. `review` means the scenario is written and its intent needs review.

From the repository root:

```sh
node turbo/apps/api/test-rebuild/reconcile.mjs --partial
node turbo/apps/api/test-rebuild/reconcile.mjs
```

The first command updates checkpoint coverage. The second requires exact coverage of the frozen IDs and passes on the final inventory checkpoint. Neither command reads the test files, so both still run after the deletion commit.

## Step 2: BDD selection

The second step selects, in a positive pass, the higher-value half of the frozen BDD scenarios for the rebuild. It writes no tests, rewrites no BDD, and leaves the frozen BDD text unchanged.

### Standard

Cases are judged from the perspective of a user or third-party caller, such as a webhook sender, CLI, Runner or integration: what the caller can trigger and what consequence they can observe. Cases closer to the user rank higher. Selected cases carry one basis:

- `core-path`: the core success path for a user or caller.
- `visible-result`: a result the user can see.
- `business-rule`: an independent business rule.
- `access-isolation`: a permission or data-isolation outcome a user can actually encounter.

These lose points:

- extreme edge cases;
- cases a user would struggle to construct;
- cases that only describe internal implementation;
- negative assertions, tombstone tests and repeated parameter variants.

A negative case is selected only when it protects a unique, important outcome a user can encounter. Copy review, isolatePg counts, BDD verification, and dependence on isolatePg, a private store or a logger are not selection criteria.

### Method

Each file has a quota of `ceil(N/2)` expanded cases. A file selects more only when key user scenarios cannot be replaced. It selects fewer, possibly none, only when its remaining cases are not reachable by a user: configuration, library, adapter, protocol, telemetry, caching or retry internals, precise race interleavings, contrived provider-failure combinations, or test fixtures. Each exception has a one-line reason. Unselected cases are recorded as `not-selected` without per-case reasons.

2. **Top-up pass.** The first pass had treated user-reachable variants as grounds for selecting fewer. That is narrower than the rule, so 171 route files below quota were re-examined. A file stopped below quota only when its remaining cases are not user-reachable. This pass added 472 cases and removed none.

### Batch B03, file warm-up and split rule

**File-level warm-up.** `testContext()` now runs a `beforeAll` warm-up in each file. It opens a case database scope, sends one side-effect-free `GET /health` request through `setupApp`, and runs one `select 1` on the shared pool. It builds no business state, adds no private entry point and changes no production code. On a light route, the first case measured 64–69 ms without the warm-up, 38–41 ms with only the health request, and 23 ms with the health request plus the pool round trip. Later cases measured 7–11 ms. **Timing method.** The coordinator runs every file once while no writer is running. A case at or below 180 ms in that run is accepted. A case between 180 and 250 ms is rerun three times and judged by its median. Writers check only correctness.

**`friend-referrals-002`.** The HTTP 500 on `POST /api/webhooks/stripe` was a test preparation gap, not a product defect. The referrer's Clerk membership list was not configured, so `getMemberRoleAndUpdateCache$` read `.data` of `undefined` at `auth.service.ts:170`. A real Clerk response always has `data`. A second gap was a renewal invoice paid before the Stripe subscription moved to the new period, which real Stripe does not do. With both fixed, the case passes at 267 ms and returns to `revisit` under the split rule.

**Split rule.** Ethan decided to keep the 200 ms limit. A multistep case over 200 ms is split into segments. Each segment builds its own Given and covers one part of the When/Then, and the segments together cover every Then of the selected ID. Segment titles carry the ID with a counter, such as `webhooks-google-calendar-011 (2/3)`. A case is recorded as `slow-setup` only when its Given plus the first When/Then already exceeds 200 ms, with segment timings as evidence. The existing `slow-setup` records and the timed-out `revisit` IDs are reviewed one by one, core user paths first.

### Round 10: CI noise, commit gate and first splits

**Commit gate.** Before each commit the coordinator runs a self-check on the changed test files. It is not a test assertion. It fails on an empty `describe`, any MSW request without a matching handler, any business `[WARN]`/`[ERROR]` log printed while a case runs, unhandled errors and failing cases. A business log passes only when [gate-allow.tsv](gate-allow.tsv) lists it for that case ID because the case's own Given or When drives that failure path. The settle step refuses a file whose current content has not passed the gate. One whole-suite run with four workers passed on 115 files after the fixes.

**CI fixes.** The empty `client-generated shared-thread IDs` suite was removed. `integrations-slack-004` and `integrations-slack-status-004`, `-008` and `-011` now configure Slack's `chat.postMessage` answer through the shared Slack app doubles. `slack-connector-oauth-015` answers `POST https://slack.com/api/auth.revoke`. `billing-auto-recharge-007` configures the Stripe customer and invoice doubles, because enabling below the threshold starts a recharge. `billing-usage-pack-credits-004` no longer depends on the order of two grants that expire at the same time.

**Split rows.** A split ID has one Vitest row per segment, titled `<id> (k/n)`. The ledger keeps one line per ID, with the slowest row as `duration_ms` and every row's duration in the note (`split n=3: 1/3=…; 2/3=…; 3/3=…`).

**Slow-setup review.** Each reviewed case was measured as its own Given plus its first When/Then. Measurements taken while other writers loaded the two-CPU machine are kept as slow-setup only when every run exceeded about 230 ms. Borderline cases are revisits to be measured again on an idle machine.

**First-test cold start.** The first case that reaches a code path in a file costs about 100–150 ms more than the same case later in the file, even with the file warm-up. Without the warm-up the same first cases took 294–309 ms instead of 243–246 ms. When a first case is removed for being slow, the next case inherits the cost. For that reason several committed first cases now measure 208–282 ms locally after their 95–185 ms acceptance. Split rows that pass but sit in such files are revisits until the handling of this cost is decided.
