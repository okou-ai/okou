# vnc-needs-rebind

## vnc-needs-rebind-001

- Vitest: "VNC depends on current SSH binding > keeps an SSH provider dependency separate from native VNC role authority"
- Mode: run
- Given: A Pro member has a running chat Run on an authenticated Runner. The member saves a personal Cloudflare Access configuration, creates an SSH connection routed through it, and creates a VNC host at `127.0.0.1` tunneled through that SSH connection. Chat defaults are enabled for both the SSH and VNC hosts. The clock is 2026-10-14T00:00:30Z.
- When: The Runner calls `POST /api/runners/runs/:runId/vnc/resolve` declaring only Cloudflare Access and Tailscale native profiles; calls `POST /api/runners/runs/:runId/vnc/check` expecting the Cloudflare Access transport; posts `POST /api/runners/runs/:runId/vnc/observations` with the SSH transport and each native failure reason (`access_rejected`, `access_tls_failure`, `access_protocol_failure`, `origin_tls_failure`, `tailscale_unavailable`), and once with a `network_failure` that names the Cloudflare Access config as the KDC transport; the member reads `GET /api/vnc/connections/observations`; finally the Runner resolves with the standard profiles.
- Then: The native-only resolve returns `{ outcome: "unsupported_profile" }` with no decryption. The check returns `{ outcome: "configuration_changed" }`. Every observation returns `{ outcome: "ignored" }` and the owner sees no observations. The standard resolve returns `resolved_transport` with the SSH transport (connection ID and generation) and contains none of the Cloudflare Access client credentials.

## vnc-needs-rebind-002

- Vitest: "VNC depends on current SSH binding > convert blocks VNC over a retained SSH host and allows explicit SSH recovery"
- Mode: run
- Given: A Pro member has a running chat Run with a chat-enabled direct VNC host. A workspace admin saved an organization-scoped Cloudflare Access configuration; the member created an SSH connection routed through it and a second VNC host tunneled through that SSH connection, with SSH and VNC chat defaults enabled. Parameter row `convert`.
- When: Before the change, the Agent lists `GET /api/vnc/hosts` and the Runner resolves and checks the tunneled host. The admin then reads the impact preview with `operation: "convert"` and converts the configuration to personal via `POST /api/cloudflare-access/configs/:configId/convert-to-personal` with the previewed revision and snapshot (HTTP 200). The member lists SSH and VNC connections; the Agent lists hosts; the Runner resolves and checks the tunneled host and resolves the direct host. Finally the member switches the SSH connection to a direct transport on port 22 via `PATCH /api/ssh/connections/:connectionId`, and the Agent and Runner repeat their reads.
- Then: Before the change, both hosts are listed, the tunneled host is `ready`, resolve returns `resolved_transport` and check returns `valid`. After the change, the SSH connection is one generation newer with transport `cloudflare_access` marked `needsRebind: true`, and the tunneled VNC host still exists. The inventory still lists both hosts, with the tunneled host `blocked` for reason `needs_rebind` and the direct host `ready`. Resolving and checking the tunneled host return `unavailable` with no decryption, while the direct host still resolves. After the SSH recovery returns HTTP 200, the tunneled host is `ready` again, resolves with the SSH transport at the SSH generation plus two, and checks as `valid` at that generation.
